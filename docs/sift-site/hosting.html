Hosting Sift

Keep the desktop local while Sift and its database connections run elsewhere. Use HTTPS for a shared server or SSH for direct access to one remote machine.

Once connected, follow Shared rooms to grant membership, bind a database connection, and collaborate. Set up tenant and room membership for everyone who will join.

What runs where?

Your desktop provides the editor and interface. The Sift server owns database connections, shared documents, rooms, and credentials. Database addresses are resolved from the server's machine, so choose a host with network access to the databases you want to use.

For HTTPS, prepare a compatible Sift server build, persistent storage, and an HTTPS reverse proxy. For SSH, start with a working system SSH connection; Sift's remote helper handles compatible server provisioning.

Database credentials stay in the server's configured secret store. They never belong in sift.toml, URLs, shell arguments, or desktop presentation state.

Hosted HTTPS

  1. Configure the instance. In sift.toml, choose transport = "network" and a durable metadata secret backend. For a shared team instance, use deployment = "team" and configure the allowed principals and tenant memberships. Disable loopback authentication bypass.
  2. Prepare persistent state. Validate the manifest, generate its lock, and review the resource plan. Import each requested credential slot into the server's secret store, then apply the plan. Apply required metadata migrations before starting the server.
  3. Publish HTTPS. Keep Sift bound to loopback when the proxy is on the same host. Forward HTTP and WebSocket upgrades on the same origin, preserving the /v1 path. Set public_base_url to that exact external HTTPS origin.
  4. Check readiness and connect. Wait for the HTTPS /v1/ready endpoint to succeed. Each person can then add that origin in the desktop, sign in, and select their tenant.

Use the configuration reference for identity, connection profiles, credentials, and tenant policy.

Private HTTPS with Tailscale

On a server already connected to your Tailnet, Tailscale Serve can publish the local Sift listener. These commands assume Sift listens on port 7474:

sudo tailscale set --operator=$USER
tailscale serve --bg http://127.0.0.1:7474
tailscale serve status

Use the HTTPS origin printed by tailscale serve status for both public_base_url and desktop connections. Tailnet access policy controls which devices can reach it; Sift sign-in and tenant membership determine what each person can access.

Wait for the HTTPS /v1/ready endpoint before connecting; first certificate issuance may take a moment. In Sift, use <leader> d c, choose a hosted server, and enter the HTTPS origin. Plain HTTP is accepted only for loopback.

Direct SSH

First confirm that your system SSH client can reach the destination. Replace the alias below with an entry from your SSH configuration:

ssh my-ssh-config-host

Open the server picker with <leader> d c, choose SSH, and enter a destination already understood by your system OpenSSH client, such as user@host or an SSH config alias. Sift preserves your host-key, agent, jump-host, and authentication policy.

The helper installs or reuses a compatible remote server, starts a private daemon, and forwards it to a local loopback port. Closing the desktop tunnel leaves durable remote state alive; reconnecting opens a fresh authenticated grant.

The remote state directory belongs to the remote OS account. Reuse that account and state directory when reconnecting to your instance. For a team instance, arrange tenant membership and a registered Sift principal key with the administrator before connecting.

Recovery and identity

EventExpected behaviour
Network interruptionSift reconnects with bounded, jittered backoff.
Server restartThe instance stays the same; process-local sessions, connections, cursors, and sockets reopen.
Different instance idSift refuses the replacement. Forget and add it again only when the change is intentional.
Expired loginInteractive sessions refresh automatically and persist rotated credentials in the OS vault.

Keep the instance's metadata and secret store on persistent storage. A reconnect restores access to durable documents, rooms, profiles, and history; active transactions and retained query results need separate attention after a restart.

If a write was interrupted, check its outcome before running it again. When connectivity fails, check the HTTPS certificate or SSH connection, then server readiness, sign-in, and tenant access in that order.
